# Swift SDK overlays built from source

Swift.org toolchains stopped shipping the Darwin SDK overlays, so the copies in this repository were x86_64-only (Swift 5.2.2). The CMake build of this repository builds six of them from source, for the architecture the Darling build produces (x86_64, or arm64 with `TARGET_ARM64`), and installs them in place of the 5.2.2 ones. Four are built from the last open-source Swift sources; `os` and `XPC` were never open source, so they are written from Apple's public API documentation and the imported symbol names (no Apple code).

arm64 code here is compiled for an ARMv8.0 baseline with outline atomics (`-mcpu=apple-a7 -moutline-atomics`) and linked with `DARLING_RT_BUILTINS` from `../runtime/build.sh`, like the runtime libraries; see `../runtime/README.md`. `-target arm64-apple-macosx` alone means Apple M1, whose LSE atomics an ARMv8.0 phone CPU traps on. `build.sh` builds the arm64 slices of the overlays that the CMake build does not (see below).

## Coverage of what macOS 26 apps import

Measured against every binary in `/System/Applications` of a macOS 26.6.2 install:

- **ObjectiveC:** 14/14 symbols.
- **CoreFoundation:** 15/15, including the `$s12CoreGraphics7CGFloatV…` metadata and conformances.
- **os:** 44/44.
- **XPC:** 21/21.
- **Dispatch:** 94/104 before `Schedulers+DispatchQueue.swift`; the missing 10 are the Combine `Scheduler` conformance of `DispatchQueue` and its `SchedulerTimeType`/`SchedulerOptions` types, which that file (`release/5.4`) now provides. `libswiftDispatch` links Combine weakly, as on macOS, so programs that do not use Combine do not need it.

## Building

The Foundation overlay also needs a checkout of apple/swift-foundation and of swiftlang/swift-cmark, both at the tag `swift-6.3.3-RELEASE` (`SWIFT_FOUNDATION_SOURCE_DIR`, `SWIFT_CMARK_SOURCE_DIR`; by default the sibling directories `../swift-foundation` and `../swift-cmark` of this repository, which the main repository provides as submodules). Configuring stops with a message when a checkout is missing. swift-cmark's C sources are compiled into libswiftFoundation with hidden visibility, so none of its symbols is exported.

`CMakeLists.txt` in the parent directory builds the overlays with the Swift toolchain that the main repository's `cmake/swift_toolchain.cmake` finds (`-DSWIFT_TOOLCHAIN=<root>` selects one, `-DSWIFT_TOOLCHAIN=OFF` skips them). Without a toolchain the overlays are skipped and the rest of the build is unaffected. The function `add_darling_swift_library` (main repository, `cmake/darling_swift.cmake`) compiles each overlay with `swiftc -frontend` for `<arch>-apple-macosx26.0` against Darling's source-tree SDK and the module interfaces in `stdlib-modules/`, and links it with Darling's ld64 against Darling's libSystem, libobjc and CoreFoundation. The overlays import each other, so the targets depend on one another in the order Darwin, ObjectiveC and CoreFoundation, Dispatch, then os and XPC.

The toolchain is the Linux Swift release matching `version.txt` (for example `swift-6.3.3-RELEASE-debian12.tar.gz` from download.swift.org); its `swiftc -frontend` cross-compiles to `apple-macosx`. The Darling SDK must contain the Clang module maps and API notes for Darwin, ObjectiveC, Dispatch, os, XPC and CoreFoundation, and the `sys/cdefs.h` default-platform fix. Without that fix, arm64 code links against `$UNIX2003` symbol variants that don't exist. The Dispatch overlay needs the libdispatch with the `OS_dispatch_queue_serial_executor` class.

## Tests

`tests/os_xpc.swift` covers `Logger`, `os_log` with arguments, signpost IDs and intervals, `OSAllocatedUnfairLock` across threads, `XPCDictionary`/`XPCArray` and `XPCSession`. `tests/objc_only.swift` and `tests/objc_cf.swift` cover an NSObject subclass with `@objc` methods and selectors, NSObject `Equatable`/`Hashable`, `autoreleasepool`, `ObjCBool`, CF types as `Hashable` (`_CFObject`), CFString round trips, and CGFloat. Build them for `<arch>-apple-macosx26.0` against these overlays, link with Darling's ld64 (plus `-Xfrontend -disable-objc-attr-requires-foundation-module`, since there is no Foundation Swift overlay), and run them with `darling shell`.

`tests/coremedia_network.swift` covers the CoreMedia and Network overlays: `CMTime` from a value and timescale and from seconds (exact, rounded, NaN, infinite), sums and differences over a common timescale, equality across timescales, the order of the kinds of time, infinities, `convertScale` with each rounding direction, and the `CMTimeRange` operations; then `NWPathMonitor`'s current path, the prohibited and required interface types, and a path update handler called once on `start(queue:)` and not again while nothing changes. It passes 31/31 under Darling in an arm64 VM, where the path is `enp0s1` (wired) then `lo`. Build it with `-Xcc -fmodule-map-file=` for `CoreMedia/shims/module.modulemap` and `Network/Sockets/shims/module.modulemap`, `-import-objc-header tests/coremedia_network.h`, and link `libswiftCoreMedia.dylib` and `libswiftNetwork.dylib`. `DARLING_SWIFT_SDK_OVERLAYS_ONLY=1` builds the force-load overlays with CoreAudio and CoreMedia, after the Darwin overlay and before the ObjectiveC one; Network needs Foundation, so only the full build rebuilds it.

## Foundation coverage

The Foundation overlay is intentionally partial. Of the 4452 names the Swift 5.2.2 `libswiftFoundation` exported, 1298 are still exported by macOS 26 and were missing from the first source build. The files taken from `release/5.4` of apple/swift (commit 845205b4407cb1e50ebe69a4d1174714338337c3, `stdlib/public/Darwin/Foundation`) close most of that gap: CocoaError, URLError, POSIXError, MachError (`NSError.swift` split by type), ErrorUserInfoKey, URLResourceValues and the URL bookmark and resource value members (`URL.swift`), NSValue bridging of NSRange and the CoreGraphics types (`NSValue.swift.gyb` expanded with that commit's `utils/gyb.py`), `NSGeometry.swift`, the NSArray, NSSet, NSDictionary, NSIndexSet, NSData, DispatchData, NSExpression and NSSortDescriptor extensions, and the NSString-backed String and StringProtocol members (adapted, see `NSStringAPI.swift`). Each file keeps Apple's header and a note on what was adapted for Darling's headers. `URLComponents.rangeOfX` is written for Darling's Swift-implemented URLComponents.

The Combine integration is now built (`Schedulers+RunLoop`, `Schedulers+OperationQueue`, `Publishers+Timer`, `+NotificationCenter`, `+URLSession`, `+KeyValueObserving`, `CombineTypealiases` from the same `release/5.4` commit; `Schedulers+Date.swift` is reduced to the `Stride` typealias because `Date.swift` already declares the members) together with the `TopLevelEncoder`/`TopLevelDecoder` conformances of the JSON and property-list coders; `tests/combine.swift`, `combine_merge.swift`, `combine_combine_latest.swift`, `tests/foundation_publishers.swift` and `tests/kvo_publisher.swift` cover them. `Measurement` (`Measurement.swift`, same `release/5.4` commit, `tests/measurement.swift`) needs Foundation's API notes to import NSUnit, NSDimension, NSUnitConverter, NSUnitConverterLinear and the NSUnit<Dimension> classes as Unit, Dimension, UnitConverter, UnitConverterLinear and Unit<Dimension>. It does not include `Measurement.FormatStyle` and `formatted()` (swift-foundation only has a stub of them outside Apple's own build), `Locale.MeasurementSystem` or `Dimension.init(forLocale:)`. Still missing, each blocked outside this repository: URLResourceValues properties whose resource keys or types are not in Darling's NSURL header, NSURL promised-item and temporary resource value methods, NSCoder/NSKeyedUnarchiver top-level decode methods, NSProgress refined properties, Calendar weekend searches, URLComponents/URLQueryItem bridging, `PlaygroundQuickLook` members. The names that the other still-prebuilt overlays import from libswiftFoundation all resolve (checked with `llvm-nm -m`). The overlay needs the Foundation headers and API notes with the Swift names (NS_OPTIONS/NS_ENUM, bridges, DateFormatter, typed resource keys) in the SDK.

## CryptoKit

`../CryptoKit.framework/Versions/A/CryptoKit` is [swift-crypto](https://github.com/apple/swift-crypto) (Apache-2.0) built as module `CryptoKit`, from the `darling/cryptokit-module` branch of the fork at [cristim/swift-crypto](https://github.com/cristim/swift-crypto), pinned in `build.sh` by commit rather than by branch so the build stays reproducible. The fork's `DARLING-CHANGES.md` is the authoritative list of how it diverges from upstream; the summary is:

- Every source file opens with `#if canImport(CryptoKit)` / `@_exported import CryptoKit`. `canImport(CryptoKit)` is **true when the module being compiled is itself named CryptoKit**, so building the package this way collapses it into an empty module that re-exports itself. The fork's guards also test `!DARLING_CRYPTOKIT_MODULE`, and `build.sh` passes `-D DARLING_CRYPTOKIT_MODULE`.
- Two sites qualify types as `Crypto.Digest` / `Crypto.MessageAuthenticationCode` to disambiguate from same-named associated types. There is no `Crypto` module under `-module-name CryptoKit`, so the fork names `CryptoKit.` instead.
- Darling cannot link BoringSSL into this framework, so the fork adds a pure-Swift SHA-256 (FIPS 180-4) supplying `DigestImpl`, replacing the BoringSSL-backed one.

**Scope.** SHA-256 and HMAC-SHA-256, plus `SymmetricKey`, `Digest`/`SHA256Digest`, `HashFunction`, `HashedAuthenticationCode` and `MessageAuthenticationCode`. That is what the corpus binds: the app that motivated this binds 13 CryptoKit symbols, all inside that surface. SHA-384/512, SHA-3, MD5/SHA-1, AES, ChaChaPoly, key agreement, signatures and HKDF are deliberately left out. Five macOS 26 apps (Weather, FindMy, Maps, Freeform, Music) also link CryptoKit; their per-symbol demand was not re-derived, because the macOS system volume was not mounted, so the boundary may need widening.

**Correctness.** The fork's `Darling/run-vectors.sh` builds the same subset natively for the host and runs published vectors: NIST FIPS 180-4 SHA-256 (empty, `"abc"`, the 448- and 896-bit messages, one million `'a'`), the same one-million-`'a'` digest recomputed in 1, 7, 63, 64, 65, 127 and 1000-byte chunks to exercise the block buffer across the 64-byte boundary, value semantics when a half-fed hash is copied, and RFC 4231 HMAC-SHA-256 cases 1, 2, 3, 4, 6 and 7. 21/21 pass. That evidence comes from a **native Linux build of the identical sources**, not from running under Darling.

## Prebuilt overlays

The Swift runtime and the Swift 5.2.2 overlays that are not built from source yet are the unmodified files of swift.org's `swift-5.2.2-RELEASE-osx.pkg` (and the 6.3.3 runtime pkg); they stay byte-identical in this repository. The overlays name their dependencies as `@rpath/libswift*.dylib` and carry no `LC_RPATH`, and macOS 26 has no `@rpath` fallback, so `prebuilt_install.cmake` installs copies whose load-command paths differ: every `@rpath/libswiftX.dylib` dependency (and an `@rpath` install ID) becomes the absolute `/usr/lib/swift/libswiftX.dylib`. The copies are made in the build directory with the host `install_name_tool` that Darling builds from cctools-port, and are ad-hoc signed by `adhoc-sign` like every other image of the build. Only a reference to `@rpath/XCTest.framework` (a framework that comes with Xcode) is left.
